Designing Production LLM Serving Systems

Inference engine choices, routing, GPU worker lifecycle, KServe, autoscaling, failure replacement and serving observability.

Avivek Dwivedi · ~20 min · Advanced · Updated Sep 2026
vLLM KServe Kubernetes GPU Inference

An inference engine can generate tokens efficiently and still be only one component of a production system. Once the model must serve concurrent users, the engineering problem expands: which runtime should execute the model, how is traffic routed, how are GPU workers started and replaced, how do new replicas become ready, and what should trigger scaling. This article starts where inference engineering ends. It treats an inference engine as a GPU-backed worker and builds the production serving system around it.

01. Assumed inference model

A production serving platform sits around an inference engine. At the engine layer, a request moves through prefill, KV-cache-backed autoregressive decode, and dynamic scheduling. Those mechanics determine the capacity characteristics of each inference worker — its latency profile, its memory footprint, and how many concurrent requests it can usefully serve.

This article treats that engine as a serving unit and focuses on what happens around it: routing, replicas, GPU workers, model loading, KServe, scaling, and failure replacement. The inference internals — prefill, decode, KV cache, PagedAttention, continuous batching, TTFT, TPOT, scheduling — are treated separately in LLM Inference Engineering: From Prompt to Token.

System Boundary

This article owns the serving layer. Inference internals belong to the inference-engine article. API-level reliability — rate limiting, retries, quotas, provider limits — belongs to a separate reliability article.

02. The inference engine as a worker

For serving purposes, an inference engine is a GPU-backed process that owns:

  • Model execution (forward passes, token generation)
  • Request scheduling and batching
  • KV-cache memory management
  • GPU execution and distributed inference where configured
  • Token streaming to the caller

The engine exposes a service boundary — typically an OpenAI-compatible HTTP API. Everything outside that boundary is the serving platform's responsibility.

03. Inference engine choices

Production serving may evaluate multiple inference runtimes. Three well-known options are vLLM, TGI (Hugging Face Text Generation Inference), and SGLang. They implement different combinations of scheduling, batching, memory management, distributed execution, kernel integration, caching, and API serving.

This article does not declare a winner. Engine selection should be based on workload-specific measurement, not on general claims. The dimensions that matter include:

Performance

  • TTFT
  • TPOT / ITL
  • Throughput
  • GPU memory

Compatibility

  • Supported model architectures
  • Quantization support
  • Distributed execution
  • Startup behavior

Operational

  • API compatibility
  • Observability hooks
  • Configuration surface
  • Deployment integration

Workload fit

  • Batching / scheduling policy
  • Prefix caching
  • Long-context behavior
  • Concurrency headroom

Do not assume the engine that is fastest in a single-request test is the best choice under production concurrency. Benchmark under realistic load before selecting.

04. Routing — four layers that are not the same

Requests pass through multiple routing decisions before they reach the GPU. These are not the same thing and conflating them causes real engineering confusion.

  • Gateway routing — which API or service receives the request. External entry point, authentication, and request policy.
  • Model routing — which model, provider, or runtime handles the request. A tool like LiteLLM may operate at this layer to route between models or providers. LiteLLM does not perform the inference engine's internal scheduling.
  • Replica routing — which specific inference worker handles the request. Load balancing across healthy replicas.
  • Inference scheduling — when the engine runs the request and which batch it joins. This is internal to the inference engine, not the serving platform.

05. GPU worker lifecycle

Scaling an LLM worker is not equivalent to starting a lightweight stateless web service. A new inference replica must go through a multi-step lifecycle before it can serve traffic.

The steps that consume the most time are typically GPU allocation, model artifact download or mount, weight loading into GPU memory, and runtime initialization. The exact cost depends on model size, storage speed, and hardware. No specific timing values are claimed here — they should be measured in the target environment.

Engineering Note

Startup latency matters for autoscaling, burst traffic, minimum replica decisions, scale-to-zero decisions, failover, and rollout speed. A worker that takes minutes to become ready cannot respond to a traffic spike the way a stateless web service can.

06. Raw Kubernetes vs KServe

KServe does not replace Kubernetes. It adds model- and inference-serving abstractions on top of Kubernetes.

Raw Kubernetes deployment of an inference worker potentially requires directly managing Deployment, Service, health probes, GPU resource requests, scaling logic, routing, rollout logic, and configuration. This gives maximum infrastructure control and may make sense for unusual application-plus-model coupling, custom pipelines, special request lifecycles, custom runtimes, or cases where the team needs full control over every layer.

KServe provides serving-oriented abstractions — InferenceService resources, replica management, autoscaling integrations, rollout and versioning concepts, and a routing layer in front of model workers. It helps when the goal is standardized serving deployment, model-centric lifecycle management, or a Kubernetes-native AI platform abstraction.

This is not "KServe good, Kubernetes bad." It is a choice about how much serving infrastructure the platform should provide versus how much the team builds directly. A future Kubernetes-for-AI article will go deeper.

08. Serving-aware autoscaling

CPU-only autoscaling signals are often incomplete for GPU inference. A GPU-bound inference worker can be saturated on the GPU while CPU looks idle. Useful serving signals include:

  • Queued requests
  • Running requests
  • TTFT
  • Throughput
  • GPU utilization
  • GPU memory
  • KV-cache pressure (where exposed by the engine)
  • Request / token workload

No single metric is universally correct. Autoscaling has two different delays that should be understood separately:

  1. Decision delay — the time from pressure appearing to the autoscaler requesting new capacity.
  2. Capacity readiness delay — the time from a worker being requested to it being ready to serve traffic. This includes GPU scheduling, container startup, model loading, runtime initialization, and readiness checks.

Capacity readiness for an LLM worker may take significantly longer than ordinary stateless web-service scaling. This affects minimum replica decisions, scale-to-zero decisions, and how aggressively the autoscaler should respond to short spikes.

09. Worker and replica failure

Failure 1Replica Failure

An inference worker can become unhealthy or be evicted. Recovery concerns: unhealthy worker removal, rescheduling on another node, and retry semantics for the client. What happens to requests already in generation on the failed replica is engine- and configuration-dependent; the system needs a defined failure response rather than an implicit hang.

Failure 2Cold / Slow Model Startup

A cold worker must go through the full GPU worker lifecycle before it can serve. If autoscaling is based on instantaneous load, the system may request capacity too late. Pre-warming and minimum warm replicas are common responses.

Failure 3GPU Out of Memory

A worker may run out of GPU memory due to model size, KV-cache pressure, long contexts, or excessive concurrency. Responses include admission limits, context-length policy, quantization, or tensor parallelism — but no single mitigation always fixes OOM. The right response depends on which resource is the binding constraint.

Failure 4Distributed Worker Failure

With tensor parallelism, a single request spans multiple GPU workers that communicate during each forward pass. A process failure or communication error can impact the entire request group. The failure blast radius is wider than in single-replica serving. Exact behavior depends on the engine and configuration.

10. Serving overload boundary

If arrival rate remains above serving capacity, queue depth increases, TTFT increases, and timeouts may increase. At that point, capacity must be added or work must be rejected or deferred. A queue hides overload; it does not resolve it.

Architecture Decision

Unbounded queues are not a scaling strategy. If arrival rate remains above serving capacity, latency continues increasing even if requests are technically accepted.

The deeper reliability machinery — rate limiting, retry policy, retry budgets, backpressure, quotas, provider limits, bounded-memory streaming, and streaming recovery — is covered separately in Building LLM APIs Under Production Limits. This article keeps only the serving implications necessary to discuss overload and scaling.

11. Serving observability

Serving-level observability answers whether capacity is constrained by queueing, GPU execution, memory, startup, or worker health. The relevant metrics are:

Request metrics

  • Request rate
  • Success / error rate
  • TTFT
  • TPOT / output latency

Queue / capacity

  • Queue depth
  • Running requests
  • Token throughput

Infrastructure

  • GPU utilization
  • GPU memory
  • Worker health
  • Restart count

Lifecycle

  • Model readiness
  • Replica count
  • Startup time

Tools like Prometheus, OpenTelemetry, and Grafana are common examples, not mandatory requirements. Deep agent traces, prompt and version tracking, evaluations, and Langfuse-style multi-agent observability belong to a separate LLMOps article and are not covered here.

12. Benchmark methodology

Benchmark methodology — not results

This section defines how the serving stack should be benchmarked. No benchmark numbers are claimed. Actual results can be added later with full environment metadata and raw artifacts.

Fixed across runs: model, hardware, engine version, prompt/output distribution.

Compare: inference engine, replica count, load (concurrency), routing and scaling behavior.

Measure: TTFT, TPOT, throughput, queue depth, GPU memory, GPU utilization, worker readiness time.

Prefer official benchmark tooling (e.g. vllm bench serve for vLLM) over custom harnesses. Verify flag syntax against the installed version before running. Record the exact command and configuration for every run. Do not cherry-pick favorable runs.

13. Design checklist

Before production

  • Choose and benchmark inference engine under realistic load
  • Define latency objectives (TTFT, TPOT)
  • Establish concurrency limits per worker
  • Define GPU worker lifecycle expectations (startup, readiness)
  • Configure routing layers (gateway, model, replica)
  • Define autoscaling signals and thresholds
  • Set minimum replica count considering startup cost
  • Test replica failure and replacement
  • Test overload behavior
  • Configure serving observability
  • Define model rollout and rollback
  • Document infrastructure assumptions

14. System boundary

At this point we have built the serving layer: inference workers, routing, replica management, GPU lifecycle, KServe, autoscaling, and serving observability. But another production problem remains: how do we protect this system when traffic, provider limits, retries, long requests and failures interact?

Adaptive rate limiting, TPM/RPM constraints, queues, prompt caching, bounded-memory streaming, and recovery belong to the next layer.
