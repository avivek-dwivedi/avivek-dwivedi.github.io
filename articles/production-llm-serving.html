LLM Systems

Designing Production LLM Serving Systems

A systems-level look at vLLM, KServe, GPU inference, routing, queueing, autoscaling, observability and failure recovery.

Avivek Dwivedi · ~20 min · Advanced · Updated Sep 2026
vLLM KServe Kubernetes GPU Inference

Running an LLM behind an HTTP endpoint is easy. Operating it under variable concurrency, long contexts, GPU memory pressure, failures and latency objectives is a different systems problem. This article builds the serving architecture from the inference engine outward.

01. Serving is more than an inference endpoint

In development, a model call is almost trivially simple:

Client → model server → GPU

Production serving is not the same system with more copies. A realistic request path looks more like:

Client → gateway → authentication → quotas / rate limiting → admission control → request routing → inference replicas → GPU → streaming response

Around the request path sits a set of supporting systems: metrics, traces, logs, model storage, autoscaling, and deployment controls. None of these are optional for a service that carries real traffic.

Mental Model

vLLM solves important inference-engine problems. It does not by itself solve the entire production-serving platform. Similarly, KServe provides serving orchestration and infrastructure-level capabilities, but does not replace the inference engine. Neither technology should be oversimplified; they operate at different layers and each has a distinct responsibility.

02. Request lifecycle

A single inference request moves through a fixed pipeline before a single token reaches the client:

HTTP request ↓ validation ↓ tokenization ↓ queue ↓ scheduler ↓ prefill ↓ KV cache ↓ decode loop ↓ stream tokens ↓ completion

Tokenization

The prompt string is converted into token IDs. This is CPU-bound and happens before the GPU is touched. Long prompts cost more here than short ones.

Prefill

The prompt tokens are processed in a single forward pass to produce the first token and populate the KV cache for those tokens. Prefill is compute-heavy and often the dominant contributor to first-token latency.

Decode

After prefill, the model generates one token at a time, reusing the KV cache and appending each new token's state. Decode is memory-bandwidth bound and typically much cheaper per token than prefill.

KV cache

The cached key/value tensors for all processed tokens. It lets each decode step avoid recomputing the full prompt and prior tokens. KV-cache memory grows with sequence length and concurrency, and is one of the primary resources the scheduler must manage.

Streaming

Tokens are returned to the client as they are produced, rather than waiting for the full generation. Streaming changes how the client experiences latency and how the server must hold the connection and batch state.

Why TTFT and per-token latency measure different things

Time to first token (TTFT) is dominated by prefill: prompt length, queue wait, and scheduling. Per-token latency during decode is dominated by KV-cache memory bandwidth, batching decisions, and the number of concurrent sequences. A service can have fast TTFT and slow decode, or vice versa, depending on load.

Metrics to know

  • TTFT — Time to First Token. The latency from request arrival to the first generated token.
  • ITL / TPOT — Inter-token latency / Time per Output Token. Per-token cost during decode.
  • End-to-end latency — Total time from request to completion.
  • Throughput — Tokens (or requests) completed per unit time across the system.
  • Concurrency — Number of in-flight requests being processed simultaneously.

These metrics are not interchangeable. Throughput optimizations can hurt TTFT; strict per-token latency targets can reduce how many requests can be batched together. Benchmark numbers are intentionally omitted here — see Section 10 for the evidence framework.

03. What vLLM is responsible for

vLLM is the inference engine. Conceptually, it owns everything that happens between "a request is admitted" and "tokens are returned":

  • Model loading and weight initialization
  • Request scheduling
  • Continuous batching
  • KV-cache management
  • Paged KV-cache concepts (virtual memory-like paging of KV blocks)
  • Prefix reuse / automatic prefix caching where applicable
  • Token generation
  • OpenAI-compatible API serving
  • Quantized models where supported
  • Distributed inference concepts (tensor parallelism, pipeline parallelism)
  • GPU execution
Mental Model

"vLLM optimizes how many generation workloads share expensive GPU resources."

The reason continuous batching matters is that generation is not like traditional fixed-batch inference. In a classic batch, every input produces one forward pass and the batch is done. In generation, sequences finish at different times: a short answer completes in a few tokens while a long one keeps decoding. If the engine waited for a fixed batch to fill or to drain, GPU utilization would crater. Continuous batching inserts new requests into running batches as slots free up, keeping the GPU busy while sequences arrive and leave independently.

This is also why batch size for LLM serving cannot be treated like a fixed hyperparameter. The effective batch is dynamic, driven by memory (how many KV caches fit), by the mix of prompt and generation lengths, and by scheduling policy.

04. What KServe adds

Kubernetes and KServe operate at a different layer. vLLM runs the model; KServe manages the lifecycle of the thing that runs the model. KServe responsibilities include:

  • Deployment lifecycle for inference services
  • InferenceService resource abstraction
  • Replica management
  • Networking and ingress
  • Autoscaling integrations
  • Rollout / versioning concepts (canary, blue-green)
  • Model-serving infrastructure (knative, networking, queues)
  • Routing layer in front of model workers
  • Kubernetes resource scheduling (pods, GPUs, nodes)

The high-level architecture looks like:

Model storage feeds model workers (workers pull or mount weights at startup). Autoscaling observes serving demand and decides when to add or remove vLLM replicas. The full diagram is rendered in SVG below.

05. Routing, scheduling and queueing

Three things called "routing" are not the same thing and should not be conflated:

  • Gateway routing — which service or model version receives the request.
  • Replica routing — which specific inference replica handles it.
  • vLLM internal scheduling — when the engine runs the request and which batch it joins.

The full decision path:

Incoming request ↓ Which service/model? ↓ Which replica? ↓ When does the inference engine run it? ↓ Which batch does it join?

Several concerns shape this path:

  • Queue depth — how many requests are waiting. Depth itself is a load signal, not just a buffer.
  • Fairness — how the scheduler picks between requests of different sizes and priorities.
  • Long prompts — expensive prefill that can delay shorter requests.
  • Long generations — long-running decode that occupies a batch slot for an extended time.
  • Head-of-line effects — a single expensive request blocking many cheap ones.
  • Request cancellation — clients disconnect; the engine must stop work and free KV cache.
  • Admission control — rejecting or queueing requests before they consume resources.
Architecture Decision

Unbounded queues are not a scaling strategy. If arrival rate remains above serving capacity, latency continues increasing even if requests are technically accepted. A queue hides overload; it does not resolve it.

06. Scaling LLM inference

CPU utilization is often an incomplete scaling signal for GPU inference. A GPU-bound inference replica can be saturated on the GPU while CPU looks idle, or the reverse when tokenization and batching dominate. Useful scaling signals include:

  • Queued requests
  • Running requests
  • Request latency
  • TTFT
  • KV-cache pressure
  • Token throughput
  • GPU utilization
  • Memory utilization

Why a new replica is not instantly useful

Unlike a stateless web service, a new inference replica cannot serve traffic the moment it is scheduled:

  • Model weights may need to download or load from storage
  • GPU allocation may take time (scheduling, driver, device init)
  • Initialization (CUDA context, weight loading, KV-cache pools) can be expensive

Therefore autoscaling lag matters. The feedback loop below may take significantly longer than ordinary stateless web-service scaling:

Traffic spike ↓ Queue grows ↓ TTFT rises ↓ Autoscaler observes pressure ↓ New GPU worker requested ↓ Model loads ↓ Worker becomes ready ↓ Traffic redistributed

Scale-up risk: the autoscaler reacts to a spike that may already be over by the time the new replica is ready, leaving an expensive idle GPU. Scale-down risk: removing replicas while long generations are still in-flight can drop work or force retries. Both directions need hysteresis and an understanding of model load cost.

07. Failure modes and recovery

Failure 1GPU Out of Memory

Possible causes

  • Model too large
  • Excessive KV-cache use
  • Very long contexts
  • High concurrency
  • Incorrect memory configuration

Possible responses

  • Admission limits (bound concurrency or context length)
  • Model quantization
  • Tensor parallelism to split the model across GPUs
  • Lower context / concurrency policy
  • Capacity planning against real workload, not assumptions

No single mitigation always fixes OOM — the right response depends on which resource is the binding constraint.

Failure 2Queue Explosion

The overload loop:

traffic spike → queue depth rises → TTFT rises → timeout → retry → additional traffic

Mitigation concepts

  • Bounded queues (reject when full rather than pile up)
  • Request deadlines
  • Admission control at the gateway
  • Backpressure to upstream callers
  • Controlled retries with retry budgets

Failure 3Cold / Slow Model Startup

Startup is not free. It involves: fetching model artifacts, container initialization, GPU allocation, weight loading, and readiness checks. A cold replica can take long enough that autoscaling based on instantaneous load is misleading. Pre-warming and keeping a minimum number of warm replicas are common responses.

Failure 4Replica Failure

A vLLM replica can become unhealthy or be evicted. Recovery concerns: unhealthy worker removal, rescheduling on another node, retry semantics for the client, and — critically — what happens to requests already in generation. In-flight generations on a failed replica are typically lost; the system needs a defined retry or failure response rather than an implicit hang.

Failure 5Distributed Worker Failure

With tensor parallelism, a single request spans multiple GPU workers (ranks) that communicate during each forward pass. A distributed process failure or communication error can impact the entire request group, not just one sequence. Exact behavior depends on the engine configuration; the important design point is that failure blast radius in distributed inference is wider than in single-replica serving.

Failure 6Retry Storm

When many clients retry at once, retries amplify load and can make recovery harder. Use exponential backoff with jitter so retries spread out rather than synchronize.

Important

Retries must respect request deadlines and workload semantics. A retry that arrives after the original request's deadline has passed is wasted work that still consumes GPU resources.

08. Observability

Four metric categories cover the system end to end.

Request metrics

  • Request rate
  • Success / error rate
  • Latency
  • TTFT
  • Output token latency

Scheduler metrics

  • Queued requests
  • Running requests

Inference metrics

  • Token throughput
  • KV-cache utilization / pressure
  • Batch behavior

Infrastructure metrics

  • GPU utilization
  • GPU memory
  • Pod health
  • Restart count
  • Node health

Each signal answers a different question:

  • Metrics answer aggregate behavior — what is the system doing over time.
  • Logs explain events — what happened at a specific moment.
  • Traces explain individual request paths — where a single request spent its time.

Tools like Prometheus, OpenTelemetry, and Grafana are common examples; they are not mandatory, and the same categories can be served by other stacks. The categories matter more than the vendor.

11. Design checklist

Before production

  • Define latency objectives
  • Bound context length
  • Bound generation length
  • Establish concurrency limits
  • Define queue policy
  • Define request deadlines
  • Configure observability
  • Measure TTFT and output latency
  • Measure KV-cache behavior
  • Test failure recovery
  • Test overload
  • Validate autoscaling behavior
  • Define model rollout and rollback
  • Document infrastructure assumptions

12. Takeaways

  1. An inference engine and a serving platform solve different layers of the system.
  2. GPU inference scaling requires understanding queueing, model startup and inference-specific metrics.
  3. TTFT, output latency, throughput and KV-cache pressure reveal different bottlenecks.
  4. Reliability requires overload handling and recovery paths, not only additional replicas.
  5. Production claims should be backed by reproducible experiments.
