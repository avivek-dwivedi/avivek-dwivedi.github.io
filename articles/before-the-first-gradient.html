Before the First Gradient: Data and Evaluation for Model Adaptation

When is model fine-tuning justified? Establishing baselines, error taxonomy, data integrity, and evaluation design before modifying model weights.

Avivek Dwivedi · Advanced · Updated Sep 2026 · Series 02 / Article 01
Evaluation Design Baselines Error Taxonomy Data Integrity Contamination Adaptation Decision

A base model fails on a domain task. The team proposes fine-tuning. Before any gradient is computed, three questions must be answered: What exactly is the failure? Could a non-training intervention resolve it? And what evidence would prove that weight modification is the right response? This article builds the evaluation infrastructure that makes those questions answerable — and the decision framework that prevents fine-tuning from becoming the default solution to every model failure.

01. The decision problem

A base model produces incorrect, unstructured, or domain-inappropriate outputs on a particular task. The immediate instinct is to fine-tune. But the set of possible interventions is larger than "train the model":

  • Better prompting — a more carefully constructed prompt may resolve instruction-following failures
  • Structured decoding — constrained output formats (JSON schema, regex grammars) may resolve formatting failures
  • Retrieval augmentation — providing relevant context may resolve missing-knowledge failures
  • Tool use — delegating computation or lookup to external tools may resolve capability gaps
  • Different base model — a model with different pretraining or instruction tuning may already handle the task
  • SFT (supervised fine-tuning) — modifying weights to improve instruction following, output format, or domain language
  • Preference optimization — modifying weights to align output quality with human or verifiable preferences
  • Smaller specialist model — distilling task capability into a cheaper model for deployment

Each intervention has a different cost profile. Prompting is cheap to implement but adds inference latency. Retrieval requires infrastructure. SFT requires data, compute, and introduces regression risk. A specialist model requires the most investment but may reduce long-term inference cost.

The question is not "should we fine-tune?" but "which intervention is justified by the evidence?"

Architecture Decision

Always exhaust cheaper interventions before training. But do not use prompting to fix a capability limitation, and do not use retrieval to fix an instruction-following problem. Match the intervention to the error category, not to the fashion.

02. Task specification and error taxonomy

Before evaluating any model, define what "correct" means. This is the task specification. It includes:

  • Input space — what inputs the model will receive
  • Output space — what outputs are valid (free text, JSON, classification labels, structured explanations)
  • Success criteria — what makes an output correct (exact match, schema validity, semantic correctness, groundedness)
  • Failure modes — the categories of errors that matter (wrong answer, right answer wrong format, hallucinated content, missing information, unsafe output)

An error taxonomy is not a post-hoc classification of what went wrong. It is defined before evaluation and drives the scoring rubric. Without a pre-defined taxonomy, error analysis becomes cherry-picking — you find the failures that support your preferred intervention.

Error categoryDescriptionPlausible intervention
Missing knowledgeModel lacks domain factsRetrieval, different base model
Instruction followingModel understands the task but doesn't follow instructionsBetter prompting, SFT
Output formatContent is correct but format is wrongStructured decoding, SFT
Domain languageModel uses generic language instead of domain terminologySFT, specialist model
Capability limitModel fundamentally cannot perform the reasoning requiredDifferent model, specialist model
HallucinationModel generates unsupported statementsRetrieval, SFT with grounded data

03. Baseline selection

Baselines are not formalities. They are the control group for the adaptation experiment. If a baseline already solves the task, fine-tuning is unnecessary — and potentially harmful if it introduces regression.

Meaningful baselines for a model adaptation study:

Baseline A

  • Frozen base model
  • Basic prompt
  • No special formatting
  • Establishes the floor

Baseline B

  • Frozen model
  • Optimized prompt
  • Few-shot examples
  • Tests if prompting suffices

Baseline C

  • Frozen model
  • Structured output
  • Schema/grammar constraints
  • Tests if formatting is the issue

Baseline D

  • Frozen model
  • + Retrieval
  • Relevant context provided
  • Tests if knowledge is missing

Do not force every baseline into every task. Include a baseline only if it tests a specific hypothesis about the error distribution. If the task is structured classification and formatting is not the issue, Baseline C adds noise without insight.

04. Dataset construction and data integrity

The dataset is the single most important artifact in a model adaptation study. If the data is flawed, every conclusion drawn from training and evaluation is compromised.

Dataset provenance and licensing

  • Where did the data come from?
  • What license permits its use?
  • Was it generated by humans, by a model, or by a hybrid process?
  • If synthetic: what model generated it, and what prompt was used?

Deduplication and near-duplicate detection

Duplicate training examples inflate apparent dataset size and cause the model to overfit to repeated patterns. Near-duplicates (paraphrased versions of the same content) are subtler but equally damaging.

  • Exact deduplication — hash-based comparison (SHA-256, MinHash)
  • Near-duplicate detection — embedding similarity, SimHash, or fuzzy matching
  • Cross-split deduplication — ensure no example in training appears (or nearly appears) in validation or test

Data contamination

If the base model saw the test set during pretraining, evaluation scores are compromised. Contamination detection is not optional for credible evaluation.

  • n-gram overlap — check if test set sequences appear in common pretraining corpora
  • Membership inference — statistical tests for whether the model has seen specific examples
  • Canary insertion — insert synthetic canaries in the test set to detect memorization

For this study, we use a synthetic dataset generated specifically for the task, which eliminates pretraining contamination by construction. The test set is held out from the data generation prompt to avoid leakage.

Train/validation/test separation

Split related document families together. If two examples are paraphrases or share a common source, they must not span train and test — otherwise the test set measures memorization, not generalization.

SplitPurposeTypical fraction
TrainWeight updates (SFT) or prompt selection70%
ValidationHyperparameter selection, early stopping15%
TestFinal held-out evaluation — touched once15%
Critical Rule

The test set is touched once — for the final evaluation. Never repeatedly tune against the test set. If you select prompts, hyperparameters, or model variants based on test performance, you are doing validation, not testing. The test set ceases to be a generalization measure.

Synthetic data limitations

Synthetic data generated by a teacher model carries the teacher's biases, failure modes, and knowledge boundaries. It is useful for creating controlled evaluation sets and bounded training tasks, but it is not a substitute for human-verified domain data when correctness matters. Document the generation model, prompt, and filtering process.

05. Evaluation design

Evaluation is not "run the model on the test set and compute accuracy." It is a designed experiment with defined metrics, statistical awareness, and error analysis.

Metrics

MetricWhat it measuresWhen to use
Task accuracyIs the answer correct?Classification, exact match
Schema validityDoes the output match the required format?Structured output tasks
Unsupported statement rateWhat fraction of claims are ungrounded?Explanation tasks
Failure category distributionWhat types of errors occur?All tasks — drives intervention decision
LatencyHow long does inference take?Deployment feasibility
StabilityIs the output consistent across runs/inputs?Robustness assessment

Statistical uncertainty

A single evaluation run on 50 examples produces a point estimate with wide confidence intervals. For credible comparison:

  • Use enough test examples to distinguish meaningful differences (power analysis)
  • Report confidence intervals or standard errors, not just point estimates
  • Use bootstrap or Wilson intervals for proportion metrics
  • When comparing two systems, test whether the difference is statistically significant, not just whether one score is numerically higher

Out-of-distribution testing

If the evaluation set only contains examples similar to the training data, it measures interpolation, not generalization. Include out-of-distribution examples — different phrasings, edge cases, and novel inputs — to test whether the model has learned the task or merely memorized patterns.

06. The evaluation pipeline

The pipeline is linear but the decision is not. If the error analysis shows that retrieval would resolve the dominant failure category, the adaptation decision is "do not fine-tune — build retrieval." If the errors are in domain language and instruction following, SFT is justified. If the model lacks the fundamental capability, no amount of fine-tuning on this data will help — a different model is needed.

07. Reference task: technical operations assistant

To make the evaluation methodology concrete, we define a bounded reference task:

Task: Incident classification + grounded explanation Input: Sanitized incident description (synthetic) Output: { "category": one of [infra, network, db, app, security], "severity": one of [low, medium, high, critical], "explanation": brief grounded explanation } Success: correct category AND correct severity AND explanation contains no unsupported statements

This task has properties that make it suitable for the adaptation decision study:

  • Classification is measurable — exact match, no ambiguity
  • Explanation quality is partially measurable — unsupported statement rate, groundedness
  • Prompting is a meaningful baseline — a good prompt with category definitions may suffice
  • Retrieval is relevant — providing runbook context may improve explanation grounding
  • SFT is plausible — domain-specific incident language and classification patterns may benefit from weight adaptation
  • Data is synthetic — generated from controlled templates, no real customer data, no pretraining contamination

Code sample — evaluation scoring

evaluation.py — scoring with error categories 
from dataclasses import dataclass
from typing import Literal

@dataclass
class EvalResult:
    category_correct: bool
    severity_correct: bool
    schema_valid: bool
    unsupported_statements: int
    error_category: str  # from the pre-defined taxonomy
    latency_ms: float

def score_prediction(prediction: dict, ground_truth: dict) -> EvalResult:
    """Score a single prediction against ground truth."""
    cat_ok = prediction.get("category") == ground_truth["category"]
    sev_ok = prediction.get("severity") == ground_truth["severity"]
    schema_ok = all(k in prediction for k in
                    ["category", "severity", "explanation"])

    # Determine error category for failure analysis
    if not cat_ok:
        err = "wrong_category"
    elif not sev_ok:
        err = "wrong_severity"
    elif not schema_ok:
        err = "schema_invalid"
    else:
        err = "none"

    return EvalResult(
        category_correct=cat_ok,
        severity_correct=sev_ok,
        schema_valid=schema_ok,
        unsupported_statements=0,  # computed by groundedness check
        error_category=err,
        latency_ms=0.0,
    )

09. Experiment design

Experiment — Non-training baselines before fine-tuning

Methodology

Research question: Does any non-training intervention resolve the task's failures, and what is the error distribution that would justify weight adaptation?

Hypotheses

  • H1: An optimized prompt (Baseline B) significantly outperforms a basic prompt (Baseline A)
  • H2: Retrieval (Baseline D) reduces unsupported statements in explanations
  • H3: The dominant error category after best non-training baseline is "domain language" or "instruction following" — categories that SFT plausibly addresses

Independent variables

  • Prompting strategy (basic vs optimized vs few-shot)
  • Retrieval presence (with vs without context)
  • Model selection (base model vs alternative)

Dependent variables

  • Category accuracy (exact match)
  • Severity accuracy (exact match)
  • Schema validity rate
  • Unsupported statement rate
  • Failure category distribution
  • Latency per inference

Controlled variables

  • Test set (identical across all baselines)
  • Scoring rubric (identical)
  • Input preprocessing (identical)
  • Random seed (fixed for reproducibility)

Decision criteria

  • If any non-training baseline achieves >90% category accuracy → do not fine-tune for classification
  • If unsupported statements are the dominant error and retrieval reduces them → build retrieval, not SFT
  • If domain language and instruction following are the dominant errors after best baseline → SFT is justified
  • If capability limitations dominate → consider a different or specialist model

Status

  • Not executed. Methodology and infrastructure defined. No results published.

10. What evidence would cause us not to fine-tune?

This is the most important question in the article. Fine-tuning is not free — it requires data engineering, compute, evaluation, regression testing, and ongoing maintenance of the adapted artifact. The evidence against fine-tuning is:

  • A well-constructed prompt achieves acceptable accuracy — the model can do the task; it just needed better instructions
  • Retrieval resolves the dominant error — the model lacks knowledge, not capability
  • Structured decoding fixes formatting — the model produces correct content in wrong format
  • A different existing model already handles the task — no adaptation needed
  • The error distribution is dominated by capability limitations — fine-tuning on this data will not fix a reasoning deficit
  • The cost of data preparation exceeds the expected quality improvement — the ROI is negative
Engineering Principle

The default response to model failure should be diagnosis, not training. Fine-tuning is justified only when: (1) cheaper interventions have been measured and found insufficient, (2) the error distribution is consistent with what weight adaptation can address, and (3) the expected improvement justifies the cost of data, compute, and regression risk.
