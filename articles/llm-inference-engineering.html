LLM Inference Engineering: From Prompt to Token

Prefill, decode, KV cache, batching, GPU memory and the system mechanics that determine latency and throughput.

Avivek Dwivedi · Advanced · Updated Sep 2026 · Draft
Prefill Decode KV Cache Batching GPU Memory vLLM

A model can generate tokens quickly in an isolated test and still deliver poor interactive performance under production load. An LLM request is not one operation: the prompt first goes through prefill, which creates the attention state required for generation, and the model then enters an autoregressive decode loop, producing one new token at a time while reusing state from previous tokens. Once multiple sequences share a GPU, inference becomes a scheduling and memory-management problem as much as a model-compute problem. This article works from the request inward — prefill, KV cache, decode, batching, scheduling, GPU memory — and ends at the inference-engine boundary.

01. The request lifecycle

Before discussing performance, it helps to fix the path a single request takes through an inference engine. A prompt is not handed directly to the GPU. It is tokenized, scheduled, prefilled, and then decoded token by token. Each of those stages has different cost characteristics, and the stage that dominates latency changes with load.

Two phases do most of the work:

  • Prefill processes the existing prompt and produces the internal attention state required for future generation.
  • Decode repeatedly generates subsequent tokens, where each iteration depends on the previously generated sequence state.
Mental Model

Prefill processes existing context. Decode repeatedly extends it. Treating "inference" as one monolithic operation hides the reason concurrency changes behavior so dramatically.

02. Prefill vs decode

Prefill and decode have very different workload characteristics, and that difference is the root of most inference-engine behavior.

Prefill

During prefill, the model processes all prompt tokens in a single forward pass. Because many tokens are processed at once, prefill can expose a large amount of parallel compute to the GPU. The cost of prefill scales with prompt length: a 4000-token prompt requires more prefill work than a 100-token prompt.

Decode

During decode, the model generates one token per iteration. Each new token depends on the state built from all previous tokens, so the loop is sequential by nature. Per-token decode cost does not scale with prompt length the way prefill does, but it scales with the number of tokens generated and with how many sequences are sharing the GPU.

It is common to hear prefill described as "compute bound" and decode as "memory bound" as if these were universal laws. They are useful tendencies, not absolutes. Prefill often exposes more parallel compute, while decode frequently becomes more sensitive to memory bandwidth, KV-cache access, and scheduling. Whether a given workload is actually bound by compute, memory bandwidth, or scheduling depends on the hardware, the model, the kernel implementation, and the batch composition at that moment. The honest engineering statement is that prefill and decode stress different resources, and a serving system has to manage both.

Engineering Note

Prefill cost scales with prompt length. Decode cost scales with generation length. A request with a short prompt and a long output is decode-heavy; a request with a long prompt and a short output is prefill-heavy. The mix of requests in a batch determines what the GPU is actually bottlenecked on.

03. TTFT, TPOT, ITL and end-to-end latency

Only after prefill and decode are understood do latency metrics become meaningful. These metrics answer different questions and are not interchangeable.

TTFT
Time to First Token. The latency from request arrival to the first generated token. Conceptually it includes queueing, request processing, prefill, and the first decode step. It is not "pure prefill time."
TPOT
Time per Output Token. A decode-oriented measurement representing the average time to produce each output token during generation.
ITL
Inter-token latency. The actual gap observed between streamed tokens. TPOT and ITL are related but not identical: ITL reflects what the client experiences between tokens, which can include scheduling and batching effects that an average TPOT hides.
E2E latency
End-to-end latency. Total time from request start to the final token.
Throughput
Useful inference work completed over time — requests/sec, output tokens/sec, or total tokens/sec. These measure different things and should be reported explicitly.
Measurement Note

High throughput with unacceptable TTFT is not necessarily a useful serving configuration. A server can generate many tokens/sec while making users wait seconds for the first token. The metric that matters depends on the workload: interactive generation is TTFT-sensitive; bulk completion is throughput-sensitive.

04. KV cache — what it actually stores

The KV cache is one of the most frequently misunderstood parts of inference. It is not "a cache of the prompt" and it is not "a cache of the generated text." Transformer attention layers derive key and value representations from previous tokens. During autoregressive generation, those key/value tensors can be reused instead of recomputing them from scratch for every decode step.

The trade-off is direct: the KV cache saves repeated attention-state computation but consumes memory. For a model with many layers, many attention heads, and a large hidden dimension, the accumulated K/V state for a long sequence can be substantial — often comparable to or larger than the model weights themselves once enough sequences are active.

Engineering Note

KV cache stores attention key/value tensors, not text. It saves repeated computation at the cost of GPU memory. The more sequences are active and the longer their contexts, the more memory KV cache consumes.

05. GPU memory model

To reason about concurrency, a serving engineer needs a workable model of GPU memory. A loaded inference process uses GPU memory for several things at once:

  • Model weights — approximately fixed once a model is loaded.
  • KV cache — grows with the number of active sequences and their context lengths.
  • Runtime / workspace — temporary buffers used during forward passes.
  • Other allocations — CUDA context, framework overhead, activation buffers.

The critical production relationship is this: model weights remain approximately fixed for a loaded model, while sequence state grows with active workloads. More active sequences and longer contexts mean more KV-cache pressure. This is why context length is not only a model feature — under concurrency, it is a capacity-planning variable.

Engineering Note

Context length is not only a model feature. Under concurrency, it is a capacity decision. Doubling the supported context length can more than double the KV-cache footprint per sequence, and that footprint multiplies across every active request.

06. PagedAttention

The problem with naive KV-cache allocation is that sequence lengths are dynamic. In a real workload:

  • Request A generates 20 tokens.
  • Request B generates 200.
  • Request C generates 5.
  • Request D continues for a long sequence.

A serving system cannot efficiently assume all requests need identical contiguous memory growth. If each request is given a contiguous block sized for its worst case, memory is wasted on reserved-but-unused capacity. If blocks are sized for the average, long sequences overflow. This is the fragmentation and over-allocation problem.

The idea behind paged or block-based KV-cache management is to allocate KV memory in fixed-size blocks and let a logical sequence reference those blocks non-contiguously, growing as the sequence grows. vLLM's PagedAttention is one well-known implementation associated with this design[1].

This is an analogy-inspired, block-based approach to KV-memory management. It is not the case that operating-system virtual memory literally works inside the model. The mechanism is inspired by paging concepts but implemented specifically for KV-cache tensors by the inference engine.

07. Batching

In traditional inference, batching is simple: take 32 images, run one forward pass, done. Autoregressive LLM generation is different. Requests have different prompt lengths, different output lengths, different arrival times, and different completion times.

If the engine uses a fixed batch — waiting to fill a batch of N, then running until all N finish — capacity is wasted. Short sequences that finish early sit idle while long sequences keep decoding. The batch slot occupied by a finished request cannot admit new work until the whole batch drains.

08. Continuous batching

Continuous (or iteration-level) batching changes this. Instead of a batch boundary defined by all members finishing, the batch is re-evaluated every decode iteration. When a sequence finishes, its slot frees immediately and a new request can join the next iteration.

This changes the role of the inference scheduler substantially. The scheduler is no longer picking a fixed batch once; it is making a decision every iteration about what runs, what waits, and how memory is allocated.

09. The scheduler

An inference engine has to decide which token work runs during each scheduling iteration. The questions it balances include:

  • Which requests enter the active batch, and which wait?
  • How much token work can fit in this iteration?
  • How much KV-cache capacity remains?
  • How does new prefill work interact with ongoing decode work?
  • How do fairness and throughput trade off against each other?
  • How do long prompts influence latency for other requests?

Different engines implement different scheduling policies. There is no single universal scheduler, and the specifics matter when interpreting benchmark results.

10. Chunked prefill

One very large prefill can occupy significant compute time. While a long prompt is being processed, ongoing decode work for other sequences may have to wait or compete. Chunked prefill splits prompt processing into smaller chunks so the scheduler can interleave prefill chunks with decode iterations.

WITHOUT CHUNKING Large Prefill: ████████████████████ ongoing decode waits / competes WITH CHUNKING Prefill chunk → Decode → Prefill chunk → Decode → Prefill chunk

This introduces trade-offs, not a free win. Chunking can improve decode responsiveness and reduce head-of-line blocking from large prompts, but it can also increase TTFT for the chunked request itself (the prefill is split across iterations) and adds scheduler complexity. Chunked prefill is not automatically better; it is a tool for managing the interaction between prefill and decode under mixed load.

11. Cache terminology — do not conflate these

Several things in the inference ecosystem are called "cache," and conflating them causes real engineering confusion.

  • KV cache — attention state for active token sequences. Lives inside the inference engine.
  • Prefix cache — reuse of previously computed KV state when multiple requests share compatible prompt prefixes. Also an inference-layer mechanism.
  • Provider prompt cache — a provider-specific mechanism for avoiding or reducing repeated processing of matching prompt prefixes. May have provider-specific token thresholds, cache durations, pricing, and matching rules. Lives at the API/provider layer.
  • Semantic cache — application-level reuse based on semantic similarity of requests/responses. Lives at the application layer.

These are different mechanisms at different layers. KV cache is not prefix cache; provider prompt cache is not semantic cache. A request that hits a semantic cache never reaches the inference engine at all; a request that hits a prefix cache skips prefill for the cached prefix but still decodes.

12. Inference optimization map

There are many inference optimizations, and they do not all solve the same problem. Organizing them by the bottleneck they address is more useful than a flat list.

BottleneckOptimizations
Memory / KV managementKV-cache management, paged/block-based KV memory, quantization where relevant
Repeated prefix workPrefix caching
Attention computationFlashAttention, SageAttention / optimized kernels
SchedulingContinuous batching, chunked prefill, scheduling policy
Decode costSpeculative decoding
Model memory / computeWeight quantization
Multi-GPUTensor parallelism, pipeline parallelism

These optimizations do not compose into a single "turn everything on" knob. Enabling all of them is not guaranteed to improve performance, and some interact in non-obvious ways. The right set depends on the workload.

13. FlashAttention

Attention performance is influenced not only by arithmetic operations but by data movement between levels of the GPU memory hierarchy. FlashAttention introduced an IO-aware attention algorithm designed to reduce expensive memory movement by using tiling and better exploitation of on-chip SRAM[2]. The key insight for inference engineers is that GPU optimization is often about memory traffic as much as FLOPs. An attention kernel that does the same arithmetic but moves less data between HBM and SRAM can be faster even with identical FLOP counts.

14. SageAttention

SageAttention is a research direction focused on efficient, quantized attention[3]. It targets the same class of bottleneck as FlashAttention — attention memory traffic — but trades implementation complexity and numerical considerations for performance opportunities by operating on quantized representations.

It should be treated carefully. It is not universally faster than FlashAttention in all configurations, it is not a drop-in replacement in every stack, and production readiness depends on hardware, model, runtime, and kernel support. Quantized attention introduces accuracy considerations that depend on the quantization scheme and the model. Where precise claims are made, they should be tied to the relevant primary paper and the specific experimental context, not presented as universal.

Research Note

SageAttention is presented here as an optimization direction for attention memory traffic, studied as part of inference optimization. Whether it helps a specific deployment depends on kernel support, model, hardware, and accuracy requirements. It is not stated as proven production usage.

15. Speculative decoding

In normal decoding, a large target model produces one (or a few) tokens per step. Speculative decoding uses a smaller or faster draft mechanism to propose multiple candidate tokens, which the target model then verifies in a single forward pass. Accepted tokens reduce the effective number of expensive target iterations.

Speculative decoding does not always improve latency. Its benefit depends on draft quality (how often the target accepts the draft), verification overhead, hardware, batch size, and the serving workload. At high batch size, the GPU is already busy with many sequences, and the speculative overhead may not pay off. Whether it helps is workload-dependent.

16. Multi-GPU — concepts only

Two concepts show up when a model does not fit on one GPU or when a workload benefits from distributed execution:

  • Tensor parallelism — splits computation for model layers across GPUs, so a single layer's matmuls run in parallel on multiple devices.
  • Pipeline parallelism — assigns different groups of layers (stages) to different devices, so activations flow through stages like a pipeline.

Both introduce communication overhead. Multi-GPU does not automatically mean proportionally lower latency; splitting a model across N GPUs does not yield 1/N latency. Detailed distributed serving belongs to a later article — this one stays at the single-engine boundary.

17. Where vLLM, TGI and SGLang fit

vLLM, TGI, and SGLang are inference engines or serving runtimes. They sit between a model and the GPU, and implement different combinations of scheduling, batching, memory management, distributed execution, kernel integration, caching, and API serving.

Model ↓ Inference Engine ├─ vLLM ├─ TGI └─ SGLang ↓ GPU

This article does not perform a full vLLM vs TGI vs SGLang benchmark — that belongs to the serving article. For the experiments here, the design uses a single engine, vLLM, to control variables.

18. Starting a local inference server

Illustrative command — verify flags against the installed vLLM version 
# Start a vLLM OpenAI-compatible server (placeholder model name)
vllm serve MODEL_NAME \
  --dtype auto \
  --max-model-len 8192

Do not hardcode a model unless the experiment environment actually uses one. The flag set should be verified against the installed vLLM version, since flags change across releases.

19. A small TTFT streaming client

The following Python snippet measures approximate first-token latency from a streaming OpenAI-compatible endpoint. It is useful for understanding the metric, not as a primary benchmark harness.

ttft_client.py — illustrative measurement, not the benchmark harness 
import time
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY")

prompt = "Explain KV cache in three sentences."
start = time.perf_counter()
first_token_time = None

stream = client.completions.create(
    model="MODEL_NAME",
    prompt=prompt,
    max_tokens=64,
    stream=True,
)

for chunk in stream:
    text = chunk.choices[0].text
    if text and first_token_time is None:
        first_token_time = time.perf_counter()
    print(text, end="", flush=True)

end = time.perf_counter()

print()
print(f"TTFT: {first_token_time - start:.4f}s")
print(f"End-to-end: {end - start:.4f}s")

20. Benchmark approach

The experiment design keeps variables fixed and varies one dimension at a time. The primary question: how does increasing request load (concurrency) change TTFT, TPOT/ITL, throughput, GPU memory, and GPU utilization?

  • One fixed inference engine (vLLM).
  • One fixed model.
  • One fixed hardware setup.
  • Control as many variables as practical.
  • Do not compare engines in this first benchmark.
Measurement Note

This is a reproducible experiment design, not a set of measured results. No benchmark numbers are claimed in this article. When real results are collected, they will be added with full environment metadata and raw artifacts.

Experiment A — Request load

Goal: Observe how TTFT, TPOT/ITL, throughput, GPU memory and GPU utilization change as concurrency increases.

Concurrency levels

  • 1, 4, 8, 16, 32 (add 64 only if hardware safely supports it)

Hold approximately constant

  • model · dtype · input-length distribution · output-length distribution · hardware · software versions

Measure

  • TTFT p50, p95
  • TPOT p50, p95
  • ITL (if available)
  • requests/sec · output tokens/sec · total tokens/sec (if available)
  • GPU memory · GPU utilization
  • KV-cache utilization (if the runtime exposes it)

Experiment B — Prompt length

Goal: Observe how increasing prefill work affects the request, holding output length roughly constant and concurrency fixed.

Prompt sizes

  • 256, 1024, 4096, 8192 (only if supported by model and hardware)

Measure

  • TTFT · end-to-end latency · GPU memory · throughput

Optional Experiment C — Cache pressure

Goal: Increase combinations of active sequences and context length to observe KV-cache pressure.

Observe

  • KV-cache utilization · GPU memory · TTFT · throughput

Safety

  • Do not intentionally crash hardware. Do not create destructive tests. Only include if measurements can be collected reliably.

21. Using vLLM benchmark tooling

Prefer official vLLM benchmark tooling over a custom harness. The current CLI is vllm bench serve[4]. Flag syntax changes across versions — verify against the installed version's --help before running.

Illustrative — verify against installed vLLM version 
vllm bench serve \
  --backend vllm \
  --model MODEL_NAME \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 128 \
  --num-prompts 200 \
  --request-rate 10 \
  --save-result \
  --result-dir ./results

22. GPU observation with nvidia-smi

# Snapshot GPU utilization and memory
nvidia-smi

# Loop for coarse observation during a run
nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total --format=csv -l 1

nvidia-smi GPU utilization is a coarse signal. It reports the fraction of time the GPU had at least one kernel running, not how busy the GPU is in any deeper sense. A memory-bandwidth-bound kernel can report high utilization while delivering poor throughput. nvidia-smi alone is not enough for inference diagnosis; use it alongside the engine's own metrics.

23. Saturation analysis — the general pattern

As load increases, a serving system tends to follow a general pattern (written here as a systems tendency, not a claim about the local benchmark):

  • At low request load, the GPU may not have enough parallel work, so utilization is low and batching opportunities are limited.
  • As load increases, batching improves and throughput may rise.
  • Eventually serving capacity becomes constrained — by KV-cache capacity, GPU memory, compute, or scheduler limits.
  • Queueing increases, and TTFT may rise rapidly.

This is a general systems pattern. Whether the local benchmark follows it must be established by measurement, not assumed.

24. GPU utilization is not the whole story

GPU utilization alone does not tell you whether an LLM inference system is healthy. A system can show high GPU utilization and still have poor TTFT, poor throughput, or both. Possible bottlenecks that utilization hides include:

  • insufficient batching (GPU busy with small batches)
  • scheduler limits
  • memory-bandwidth pressure
  • KV-cache capacity
  • long prefills blocking decode
  • queueing
  • CPU/tokenization overhead
  • communication overhead in distributed execution

Examine a set of metrics together: TTFT, TPOT, ITL, queue depth, throughput, GPU memory, GPU utilization, and KV-cache metrics. No single number is sufficient.

25. Inference-level failure modes

Scoped to the inference engine only — API retries, rate limits, circuit breakers, quotas, and provider failover belong to future reliability articles.

Failure 1GPU OOM

Possible contributors

  • model memory · excessive active KV state · overly long contexts · excessive concurrency · runtime configuration

Responses

  • admission limits · context-length policy · quantization · tensor parallelism · capacity planning

No single mitigation always fixes OOM — the response depends on which resource is the binding constraint.

Failure 2KV-cache pressure

Active sequence state grows until the engine cannot admit new work or must evict. Manifests as rising TTFT, reduced concurrency headroom, or rejection of new requests. Responses: admission control, context limits, and understanding that capacity is set by the interaction of concurrency and context length.

Failure 3Long prompt / prefill interference

A very long prefill can occupy compute and delay decode for other sequences — a head-of-line effect at the iteration level. Responses: chunked prefill, prefill scheduling policy, and admission limits on prompt length.

Failure 4Poor batching / low utilization

GPU underutilized despite available work, often due to scheduler limits, low concurrency, or request shapes that do not batch well. Not an OOM, but a capacity failure of a different kind: the GPU is available but the system cannot fill it.

Failure 5Context-length rejection

Requests exceeding the configured max-model-len are rejected. This is correct behavior, not a bug — but it must be matched to the workload and surfaced clearly to callers.

Failure 6Distributed communication failure

With tensor or pipeline parallelism, a communication error across ranks can impact the entire request group. Blast radius is wider than single-replica serving. Detailed distributed failure handling belongs to a later article.

26. The system boundary

System Boundary

This article ends at the inference-engine layer. Routing, replicas, autoscaling, API reliability, rate limiting, retries, and guardrails belong to the serving layer and are covered in Designing Production LLM Serving Systems.

An inference server's useful capacity is not the number of requests it can accept. It is how much work it can sustain while meeting latency and memory objectives. The inference engine balances GPU compute, memory and KV-cache capacity, and scheduler time — and the right balance is what benchmarking is meant to find.
