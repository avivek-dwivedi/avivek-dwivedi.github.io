LLM Reliability

Building LLM APIs Under Production Limits

Adaptive rate limiting, token budgets, bounded queues, prompt caching, streaming recovery and failure-aware routing.

Avivek Dwivedi · Advanced · Updated Sep 2026 · Draft
Rate Limiting Token Budgets Retries Circuit Breakers Streaming Backpressure

A model API can be perfectly healthy while the application around it collapses. A traffic spike consumes the token budget. Requests begin receiving throttling responses. Workers retry. Those retries consume more request capacity. A queue grows. Queue wait becomes larger than the request's useful lifetime. Clients time out and retry again. Meanwhile streamed responses accumulate in process memory because downstream consumers are slower than the model. Nothing is wrong with the model. The control layer is wrong. This article builds that control layer around an LLM API.

01. Why RPM alone is not rate limiting

LLM APIs are constrained across multiple dimensions, not just request count. Potential constraints include:

  • RPM — requests per minute
  • TPM — tokens per minute
  • Input token limits and output token limits
  • Concurrent requests
  • Batch queue limits
  • Model-specific limits
  • Region-specific limits
  • Tenant quotas and account budgets
  • Application cost budgets

Not every provider exposes every type, and provider semantics differ. Treating rate limiting as "N requests per minute" ignores the fact that a 300-token request and a 16,000-token request have radically different capacity, cost, and latency impacts even though both consume exactly 1 RPM unit.

Engineering Note

Rate ≠ token capacity ≠ concurrency. A request that passes RPM may still fail TPM. A request that passes both may still exceed concurrency slots. Each dimension must be checked independently.

02. Small request vs large request

Consider two requests that both consume 1 RPM unit:

Request ARequest B
Input tokens30012,000
Max output2004,000
Potential reservation50016,000
RPM cost11
TPM impact50016,000

An RPM-only limiter treats these identically. A token-aware limiter recognizes that Request B consumes 32× the token budget. Under heterogeneous workloads, RPM-only limiting allows large requests to exhaust token capacity while the rate counter reports "requests remaining."

03. Token-aware admission control

Before calling the provider, the gateway should estimate input tokens, determine the requested output ceiling, and calculate a conservative token reservation:

reservation = estimated_input_tokens + reserved_output_tokens

Then check: request budget, token budget, concurrency slot, tenant quota, cost budget, and deadline feasibility. If all pass, admit. Otherwise queue, reject, defer, or route elsewhere depending on workload policy.

Illustrative implementation — not production-ready 
from dataclasses import dataclass

@dataclass
class TokenReservation:
    request_tokens: int
    reserved_tokens: int

async def reserve_capacity(request) -> TokenReservation:
    input_tokens = await estimate_tokens(request)
    reserved_tokens = input_tokens + request.max_output_tokens

    async with budget_lock:
        if not rpm_budget.can_take(1):
            raise RateLimited("rpm")

        if not tpm_budget.can_take(reserved_tokens):
            raise RateLimited("tpm")

        if not concurrency_budget.available():
            raise CapacityExceeded("concurrency")

        rpm_budget.take(1)
        tpm_budget.take(reserved_tokens)

    return TokenReservation(
        request_tokens=input_tokens,
        reserved_tokens=reserved_tokens,
    )

This code is illustrative. In a multi-instance gateway, budgets need atomic or distributed coordination rather than an in-process lock. A single-process lock does not protect budgets when multiple gateway instances share provider capacity.

04. Reservation and reconciliation

Reservation is conservative: the system reserves the maximum possible tokens (estimated input + max output) before generation begins, because it must protect capacity before knowing how many tokens will actually be used.

But actual generation often uses far fewer tokens than the reservation:

Tokens
Estimated input2,000
Max output4,000
Reserved6,000
Actual input2,000
Actual output550
Actual total2,550
Unused reservation3,450

The system must reconcile: release the unused 3,450 tokens back to the budget after generation completes. Without reconciliation, conservative reservations permanently under-utilize capacity. The exact reconciliation strategy depends on how the provider accounts for tokens — some bill on actual usage, some on reserved capacity. Do not prescribe one universal accounting strategy.

05. Dual token bucket design

A token bucket refills at a fixed rate up to a capacity ceiling. Two buckets can model RPM and TPM independently:

  • Request bucket — capacity: RPM, refill rate: RPM per unit time
  • Token bucket — capacity: TPM, refill rate: TPM per unit time

Admission requires: request_bucket ≥ 1 AND token_bucket ≥ estimated_reservation.

Provider Note

The local limiter may only approximate provider window semantics. Providers may use different algorithms internally (sliding window, fixed window, token bucket, or hybrid). Do not assume the local limiter exactly mirrors the provider's internal rate-limiting algorithm.

06. Adaptive rate limiting

A hardcoded limiter is a static ceiling. An adaptive limiter combines multiple signals into a conservative effective budget:

Configured limits + Provider feedback (remaining capacity, reset signals) + Actual token usage + Observed 429 / throttling responses + Recent error rate / latency / congestion ↓ Effective admission budget

The gateway adjusts its effective budget based on what it observes. If the provider returns throttling responses, the gateway should reduce its effective budget rather than continuing to send requests at the configured ceiling. Exact header names and signals are provider-specific — do not make provider-specific header names universal. Research current official documentation before implementing provider-specific signal handling.

07. Concurrency control

Staying below RPM and TPM does not guarantee system health. If requests take a long time, in-flight work accumulates: connections, workers, async tasks, memory, stream buffers, and provider sockets all consume resources while requests are active.

Illustrative — concurrency semaphore 
import asyncio

concurrency = asyncio.Semaphore(MAX_IN_FLIGHT)

async def handle(request):
    async with concurrency:
        return await provider_call(request)

The number should come from measured workload behavior, not an arbitrary guess. Too low wastes capacity; too high allows resource accumulation that degrades the entire process.

Little's Law

A compact queueing-theory result provides engineering intuition: $L \approx \lambda \times W$, where $L$ is the average number of requests in the system, $\lambda$ is the arrival rate, and $W$ is the average time in system. Higher latency naturally increases the required concurrency capacity for the same throughput. If average request time doubles, the number of in-flight requests at the same throughput also doubles.

08. Admission control vs queueing

These concepts are distinct and must not be conflated:

  • Rate budget — can downstream capacity afford the work?
  • Concurrency limit — can we run more work now?
  • Admission control — should this request enter the system?
  • Queue — where does admitted but not currently executable work wait?
  • Router — where should admitted work execute?

09. Unbounded queue failure

When incoming traffic exceeds processing capacity, an unbounded queue grows without limit. Memory increases. Queue wait increases. Requests become useless before they execute. Clients time out and retry, amplifying load. The system technically remains alive, but service quality has collapsed.

Architecture Decision

A queue hides overload. It does not create capacity. Bounded admission sacrifices some admission rate in exchange for bounded memory and bounded queue growth.

10. Bounded queues and workload classes

Illustrative — bounded queue 
queue = asyncio.Queue(maxsize=N)

# When full, put() blocks or raises QueueFull
# depending on policy

When the queue is full, policies include: reject, defer to async processing, drop low-priority work, route elsewhere, apply backpressure, or degrade feature/model. No single strategy is universally correct.

One queue may also be wrong. Different workload classes have different priorities:

ClassPriority
InteractiveLatency
BackgroundThroughput
Offline batchCost / completion
Agent / tool workDeadline / workflow state

Production systems may benefit from separate queues or scheduling classes per workload type.

11. Multi-tenant fairness

Without isolation, a noisy neighbor can degrade service for everyone. Tenant A sends many long-context requests; Tenant B sends short interactive requests. Without per-tenant budgets, Tenant A can consume TPM, queue space, concurrency, and cost budget, degrading Tenant B's experience.

Isolation mechanisms include: global budget, per-tenant budget, per-model budget, and optional priority or weighting. A full fair scheduler is not always necessary — per-tenant token and concurrency ceilings often suffice.

12. Deadlines

A timeout is usually local to an operation. A deadline describes the maximum useful lifetime of the entire request. These are not the same thing.

Example: a 20-second total deadline. Queue wait consumes 4 seconds. The provider attempt consumes 10 seconds. Only 6 seconds remain. The retry decision must use the remaining budget, not a fresh independent timeout.

Do not give every layer an independent 60-second timeout. That produces a worst-case of 60 + 60 + 60 + 60 seconds — far beyond any useful request lifetime. Propagate the deadline and let each layer use the remaining budget.

Timeout types in streaming systems

Streaming systems need more than one timeout concept:

  • Connection timeout — establishing the connection
  • Queue timeout — waiting for admission
  • TTFT timeout — waiting for the first token
  • Inter-token timeout — gap between streamed tokens
  • Provider request timeout — the overall provider call
  • Overall deadline — the request's useful lifetime

A stream can connect successfully, return the first token quickly, then stall midway. That is a different failure from connection failure, and it requires a different timeout.

Not every error should be retried. A failure taxonomy:

14. Exponential backoff and jitter

Without jitter, 100 failed requests all wait the same delay and retry simultaneously, creating synchronized spikes that keep the provider overloaded. With full jitter, retries spread across a time range.

Illustrative — deadline-aware retry with full jitter 
import asyncio, random, time

deadline = time.monotonic() + 20

for attempt in range(MAX_ATTEMPTS):
    remaining = deadline - time.monotonic()
    if remaining <= 0:
        raise DeadlineExceeded()

    try:
        return await provider_call(timeout=remaining)

    except RetryableProviderError:
        if not retry_budget.allow():
            raise

        max_sleep = min(BACKOFF_CAP, BACKOFF_BASE * (2 ** attempt))
        sleep = random.uniform(0, max_sleep)

        if sleep >= remaining:
            raise DeadlineExceeded()

        await asyncio.sleep(sleep)

Production handling should also consider provider Retry-After semantics, per-provider error classification, request idempotency, and stream state.

15. Retry budget

Suppose 100 original requests arrive during an incident. If all retry three times, downstream attempts can reach 400 total calls — exactly when downstream capacity is already unhealthy.

A retry budget caps the total retry traffic the system can generate. Once consumed: fail fast, degrade, fallback, or return an explicit error — rather than amplifying the incident.

Normal traffic: ████████████████ Allowed retries: ███ Once consumed: fail fast / degrade / fallback

A retry budget is separate from a per-request retry count. A per-request limit of 3 retries still allows 100 requests × 3 = 300 retry attempts. A retry budget limits aggregate retry traffic regardless of how many individual requests are in flight.

16. Circuit breaker

A circuit breaker stops sending traffic to an unhealthy downstream, giving it time to recover.

Three states:

  • CLOSED — normal calls flow
  • OPEN — requests fail fast or route elsewhere
  • HALF-OPEN — limited probes test recovery

A breaker should be scoped to provider, model, region, or deployment — not one global "LLM breaker." Different downstream targets can have different health states. Do not trip provider-health breakers for client-side malformed requests (4xx); those are not provider failures.

17. Capability-aware fallback

Fallback is not "try OpenAI, except use another provider." It requires capability compatibility. A route may require streaming, tool calling, structured JSON output, specific context length, vision, region, latency target, price ceiling, or a specific model family.

Engineering Note

Fallback is a semantic decision, not only an availability decision. A provider that lacks tool-calling support cannot substitute for one that has it, regardless of health. The capability filter runs before the routing policy.

18. Cost-aware routing

Cost can be estimated conceptually: estimated_cost ≈ (estimated_input_tokens × input_price) + (reserved_output_tokens × output_price). But pricing rules differ by provider and model: cache discounts may reduce cost, batch APIs may use different pricing, and reasoning-token accounting may differ by model. Do not hardcode prices unless intentionally researched for a dated example.

Routing can consider capability, latency, health, cost, and region. Do not advocate "always choose cheapest" — the cheapest model may lack required capabilities or have unacceptable latency.

19. Batching terminology

Three things called "batching" are not equivalent:

  • Inference engine batching — inside vLLM / SGLang. Continuous batching of decode iterations. Covered in the inference article.
  • Application micro-batching — the application groups several units of work before sending downstream.
  • Provider Batch API — asynchronous, offline provider-side processing with different pricing and completion semantics.

These are not the same mechanism and should not be conflated.

Offline batch workloads

Workloads that may suit asynchronous batch processing: evaluation, data enrichment, classification, embeddings, large offline extraction, nightly processing. Poor fit: interactive chat, live copilot, low-latency agent execution. Do not hardcode vendor completion guarantees unless researched and dated.

20. Prompt caching

Consider two requests that share a large stable prefix (system instructions, tool schemas, reference content) but differ only in the user question at the end. Most of the prefix is identical across requests.

Stable Prefix: ██████████████████████████ Dynamic Suffix: ██

The engineering principle: place stable, reusable context earlier where provider or runtime caching semantics benefit from common prefixes. Keep highly dynamic, request-specific information later where possible.

Provider Note

Provider cache matching rules, minimum cacheable tokens, TTL, cost discounts, and quota implications are provider-specific. Do not state exact values unless current official documentation confirms them. Write dated claims as "at the time of this article" with provider and model scope.

Cache terminology — do not confuse

  • KV cache — active model attention state (inference engine layer)
  • Prefix cache — reuse of computed prefix KV state (inference engine layer)
  • Provider prompt cache — provider-managed repeated-prefix compute/cache mechanism (API/provider layer)
  • Semantic cache — application-level response reuse based on semantic similarity (application layer)

When prompt caching does not help

  • Prefix changes every request
  • Dynamic data placed very early in the prompt
  • Short prompts below provider/runtime thresholds
  • Small traffic volume with little prefix repetition
  • Cache TTL expired
  • Provider or model changed
  • Cache semantics differ from assumptions

21. Semantic cache boundaries

Request ↓ Embedding ↓ Similarity search ↓ Suitable cached response? ├── yes → return response └── no → call LLM

Potentially useful for: stable FAQs, highly repetitive low-risk requests, expensive repeated generation. Potentially dangerous for: personalized requests, time-sensitive requests, authorization-dependent responses, agent actions, rapidly changing knowledge, high-stakes outputs, context-rich conversation.

Architecture Decision

Semantic similarity is not semantic equivalence. A request that is semantically similar to a cached response may differ in authorization, personalization, temporal context, or required precision. High-risk use cases should generally avoid careless semantic reuse.

22. Streaming reliability

The naive implementation accumulates the full response in memory:

Naive — unbounded accumulation 
full_response = ""
async for chunk in provider_stream:
    full_response += chunk

Under long outputs × many concurrent streams × slow consumers, memory can grow significantly. The broader problem is unbounded buffered state, not string concatenation specifically.

Bounded streaming pipeline

Illustrative — bounded stream buffering 
queue = asyncio.Queue(maxsize=32)

async def producer():
    async for chunk in provider_stream():
        await queue.put(chunk)  # blocks when full

async def consumer():
    while True:
        chunk = await queue.get()
        try:
            await persist_chunk(chunk)
            yield chunk
        finally:
            queue.task_done()

await queue.put() becomes backpressure when the consumer cannot keep up. This is not production-ready as-is — it demonstrates the mechanism, not a complete streaming server.

Three streaming failure types

  • Client failure — provider may still be generating. Cancel upstream? Continue and persist result? Depends on workload.
  • Application worker failure — provider may still be alive but our proxy process disappears. If stream state lives only in memory, delivery state is lost.
  • Provider stream failure — upstream generation itself terminates. Fundamentally different from client or worker failure.

23. Delivery resume vs generation resume

This distinction is critical.

Delivery resume — generation completed or is still active. The system persisted chunks. The client disconnected. The client reconnects with a request ID and last sequence number. The server replays missing chunks and joins the live stream if still active. This is transport/delivery recovery.

Generation recovery — the provider-side generation itself failed. A generic external provider does not expose the model's exact internal decode or KV state for resumption at token N. Recovery may require restarting the request or creating a continuation using persisted context and output. This is a new generation and may diverge. Never claim generic provider streams can always resume generation exactly.

Engineering Note

Delivery resume ≠ generation resume. Delivery resume replays persisted chunks. Generation recovery requires a new generation and may produce different tokens. These are different problems with different solutions.

Durable stream record

A conceptual persistence model for stream recovery:

FieldPurpose
request_idCorrelate request across retries and reconnects
sequence_numberOrder chunks within a stream
chunkThe streamed content
created_atTimestamp
statusPENDING · RUNNING · COMPLETED · FAILED · CANCELLED
provider_request_idWhere available, for provider correlation

Persistence options

PostgreSQL, Redis Streams, Kafka, durable event stores, or object storage for large artifacts. Trade-offs: latency, durability, ordering, retention, fan-out, operational complexity. Given the broader portfolio, PostgreSQL may be used in examples where a relational durable record is sufficient. This is not a technology shootout.

24. Idempotency

Even pure generation retries can duplicate cost. Tool and agent work can duplicate side effects. An idempotency key controls duplicate execution:

idempotency_key ↓ existing execution? ├── yes → return / rejoin existing result └── no → execute and store result

Store conceptually: idempotency key, request hash, state, and result reference. On a duplicate request with the same key, return or rejoin the existing execution. On a conflicting payload with the same key, reject.

Provider Note

Idempotency helps control duplicate execution. It does not guarantee exactly-once execution across distributed systems. Network partitions, process crashes, and partial completions can still produce edge cases. Design for at-least-once with idempotency, not for strict exactly-once.

25. Bounded-memory design

Suspicious structures to audit in an LLM API:

  • Unbounded request queue
  • Unbounded stream buffer
  • Unbounded retry queue
  • Unbounded batch accumulator
  • Unbounded conversation state
  • Unbounded result aggregation

Replace them with explicit limits: max queued requests, max concurrent requests, max prompt tokens, max output tokens, max stream chunks in RAM, max persistence batch size, max per-request retained state.

Engineering Note

Move large state through the system. Do not accumulate it indefinitely inside the process. Bounded memory is not a performance optimization — it is a reliability requirement.

Backpressure

End-to-end backpressure: database slows → persistence consumer slows → bounded queue fills → producer cannot enqueue → upstream read slows or request policy activates. Contrast with an unbounded queue that grows forever when the database slows. Exact upstream backpressure behavior depends on SDK, HTTP implementation, and provider. Do not claim every streaming API perfectly propagates TCP backpressure to model generation.

26. Operational guardrails

Operational resource controls protect capacity, cost, and availability:

  • Max input tokens · max output tokens · max payload bytes
  • Max concurrency per identity · max requests per period
  • Max daily token budget · max cost budget
  • Allowed models · maximum stream duration
  • Maximum tool / agent iterations where applicable
  • Tenant quota

These are operational safety controls, not content moderation. Prompt injection, model alignment, harmful-content moderation, and jailbreak research deserve separate treatment.

Abuse and cost amplification

Examples of cost-amplification patterns: repeated max-context requests, repeated max-output requests, parallel requests from one identity, expensive model selection abuse, long-running streams, agent loops. Quotas and resource limits reduce cost-amplification risk. They do not solve all security or safety concerns.

Where providers expose request IDs, retain them. Generate an internal request ID and correlate: internal_request_id, provider_request_id, tenant_id, attempt_id, stream_id. This helps reconstruct retries and fallbacks. Do not hardcode provider-specific header names until verified.

28. Reference architecture

This is a reference architecture, not the only valid topology. The control plane holds RPM/TPM budgets, tenant quotas, cost budgets, provider health, circuit state, and route configuration. The data plane flows through gateway, identity, token estimation, admission, bounded queue, router, providers, stream manager, and durable state. Telemetry originates from every layer.

29. Benchmark methodology

Benchmark methodology — not results

This section defines how the reliability control layer should be benchmarked. No benchmark numbers are claimed. The experiment lab uses a mock provider so failure conditions can be tested without burning real API quota.

Experiment 1 — RPM-only vs RPM+TPM

Goal: Show why request-count limiting alone is insufficient for variable-sized LLM workloads.

Workload

  • 80% small requests, 20% large requests

Compare

  • A: RPM-only limiter · B: RPM + TPM limiter

Measure

  • Admitted · rejected · throttled downstream · token utilization · queue depth · p95 latency · successful throughput

Hypothesis: Token-aware admission should better protect downstream token capacity under heterogeneous request sizes.

Experiment 2 — Unbounded vs bounded queue

Goal: Compare unbounded queue vs bounded queue with explicit admission under load above capacity.

Measure

  • Process memory · queue depth · queue wait · successful completions · rejections · request latency

Hypothesis: Bounded design sacrifices some admission rate for bounded memory and bounded queue growth.

Experiment 3 — Retry synchronization

Goal: Compare fixed retry delay vs exponential backoff with full jitter during a simulated provider outage.

Measure

  • Attempts/sec over time · successful recovery · retry traffic · provider overload after recovery

Experiment 4 — Retry budget

Goal: Compare unlimited retry vs bounded retry budget during a simulated outage.

Measure

  • Downstream attempts · successful original requests · retry amplification · time to recover

Experiment 5 — Prompt cache structure

Goal: Compare stable prefix + dynamic suffix vs dynamic content placed early, against a provider/runtime whose caching behavior can be measured.

Record if exposed

  • Cached token count · uncached input tokens · latency · cost · quota behavior

If real provider access is unavailable, keep as reproducible methodology only. Do not fabricate cached-token results.

Experiment 6 — Stream delivery recovery

Goal: Start streaming, persist numbered chunks, disconnect client, reconnect using request_id and last_sequence_id, replay missing chunks.

Measure

  • Duplicate chunks · missing chunks · replay delay · buffer memory

Experiment 7 — Provider stream failure

Goal: Cause mock provider to terminate mid-generation. Show that delivery replay recovers persisted chunks, but continuation after provider failure requires a new generation strategy.

30. System boundary

System Boundary

The reliable unit is not the model call. The reliable unit is the controlled execution around the model call. A production LLM API must continuously balance token capacity, request rate, concurrency, latency, memory, cost, and downstream health. Once those controls exist, the next operational question becomes: how do we observe request, model, retrieval, tool and agent behavior across the entire system?
